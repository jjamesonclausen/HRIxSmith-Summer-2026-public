# Appendix: AI-Use Lessons and Recommendations

## Purpose and Evidence Basis

This appendix records practical advice for a future team using an LLM wiki, AI-assisted CAD, and general-purpose AI tools during an engineering design project. It synthesizes Anna's and Julie's daily logs, the project technical-report draft, CAD records, prompting experiment, and Obsidian notes. It reports project observations, not universal performance claims about any model or software. (source: `active/_anna daily log.md`; source: `active/_julie_daily_log.md`; source: `active/documentation/Technical Report Draft - 2026-08-03.md`; source: `active/documentation/CAD Modeling Process.md`; source: `active/analysis/LLM Prompting Experiments.md`)

## Summary Advice

Use AI to make the work more visible, searchable, and testable, not to replace technical judgment. The most successful workflow was human-led: people defined the problem, curated evidence, set criteria, inspected outputs, and made decisions; AI retrieved across the curated record, organized material, produced transparent first drafts, generated alternatives, calculated explicit scoring systems, and supported explanations and quizzes. This division retained the speed benefit while limiting automation bias. (source: `active/_anna daily log.md`; source: `active/_julie_daily_log.md`; source: `active/documentation/Technical Report Draft - 2026-08-03.md`)

Build the information system before relying on it. Keep immutable raw sources separate from agent-editable notes, require source citations and explicit labels for inferences, and create small, task-specific procedures for repeated work such as PDF conversion, image extraction, source ingestion, and link checking. Early general instructions were not sufficient: the agent sometimes summarized source text, omitted figures, equations, or metadata, created malformed links, and stopped before verification. Splitting durable project rules from precise task procedures, then revising those procedures in response to observed failures, improved consistency. (source: `active/_anna daily log.md`; source: `active/_julie_daily_log.md`; source: `active/documentation/Technical Report Draft - 2026-08-03.md`)

Treat the LLM wiki as a curated research partner rather than an authority. It was highly useful for comparing many trusted sources, surfacing design alternatives, organizing candidate work plans, and teaching through explanations and quizzes. It was not reliable enough to accept quantitative extraction, graph interpretation, a source-context match, or a consequential ranking without checking the primary evidence. The VJ20 cut-in-speed misreport demonstrates that a plausible value can be taken from the wrong design or experimental context. (source: `active/_anna daily log.md`; source: `active/_julie_daily_log.md`; source: `active/documentation/Technical Report Draft - 2026-08-03.md`)

Make learning intentional. Fast synthesis can bypass the direct reading and struggle through which technical understanding is built. Read key sources, independently rank or reason about important decisions before viewing the AI result, ask the wiki to teach and quiz at the desired conceptual level, and explain the conclusion back in one's own words. A fast answer should create a better question or a testable next step, not end the investigation. (source: `active/_anna daily log.md`; source: `active/_julie_daily_log.md`; source: `active/resources/Julie reflections on the wiki, LLM, and AI.md`)

Use CAD agents for constrained first-pass geometry, not final engineering geometry. Supply source-backed parameters and prohibited features, distinguish inferred hardware from source facts, keep unknowns editable, and record the prompt and response. Inspect every revision visually and, where relevant, through geometry checks for airfoil identity and orientation, blade and strut count, phase, connectivity, intersections, watertightness, and CFD face selection. A model that executes, renders cleanly, or reports fully constrained sketches can still have floating parts, missing struts, an incorrect airfoil, or separate touching bodies. (source: `active/documentation/CAD Modeling Process.md`; source: `active/documentation/CAD log/a_vj20.md`; source: `active/_anna daily log.md`; source: `active/_julie_daily_log.md`)

Maintain rich, contemporaneous records. Detailed daily logs captured actions, decisions, unsuccessful attempts, observations, questions, and evolving hypotheses. They later allowed the LLM to generate useful documentation outlines, meeting summaries, reflection prompts, and this type of retrospective analysis. Similarly, exporting CAD-agent conversations into the repository made the assumptions, prompts, claimed checks, and discovered errors accessible to the LLM wiki and future reviewers. These logs are project context, not merely administrative records. (source: `active/_anna daily log.md`; source: `active/_julie_daily_log.md`; source: `active/documentation/CAD log/a_vj20.md`)

## Recommended Operating Pattern

1. Define the engineering question, success criteria, evidence threshold, and decision owner before asking an AI tool for output.
2. Add sources and project records to a structured repository; preserve raw material and require traceable claims in derived notes.
3. Create a narrow procedure and a small evaluation set for every recurring high-risk task; revise the procedure when a failure is observed.
4. Ask AI for a bounded first pass, alternatives, or a transparent calculation. Require assumptions, unknowns, source references, and the requested output format.
5. Independently inspect the evidence and artifact. Verify every value that affects a decision against the primary source or original output, especially values read from figures, values with units, and values that depend on scale or test conditions.
6. Record the prompt, result, review outcome, changes made, and unresolved questions in the daily log or relevant technical log.
7. Escalate from AI advice to documentation, direct calculation, a domain-specific tool, or a human expert when the tool lacks the necessary context, cannot inspect the relevant artifact, repeats generic advice, or cannot support a high-consequence claim.

## Issues, Gaps, and Recommended Responses

| Category | Observed or anticipated gap | Why it mattered | Recommended response | Evidence |
| --- | --- | --- | --- | --- |
| LLM wiki | General rules alone did not reliably make the agent complete multi-step ingestion work. | Sources were sometimes summarized, incompletely converted, or left without figures, equations, metadata, links, or a final verification. | Keep high-level behavior rules separate from short, named procedures for conversion, ingestion, figure handling, maintenance, and quantitative checks. Direct the agent to the applicable procedure before each task. | Anna and Julie, 2026-06-29 to 2026-07-06 daily logs; technical report draft, Section 2. |
| LLM wiki | Raw source text could be altered or summarized during conversion. | A derived summary cannot replace evidence, and changed source text weakens traceability. | Preserve immutable originals; retain complete converted text separately from summaries; review source fidelity after conversion. | Julie, 2026-06-29 to 2026-07-01 daily log; technical report draft, Section 2. |
| LLM wiki | Images, figure captions, equations, and formatting were inconsistently preserved. | Missing or misplaced visual evidence degraded readability and caused quantitative information in figures to be missed. | Use a tested extraction workflow, preserve figure captions with figures, represent unreadable equations as images when necessary, and run a post-ingestion checklist. | Anna, 2026-06-26 to 2026-07-06 daily log; Julie, 2026-06-26 to 2026-07-06 daily log. |
| LLM wiki | Source conversion and verification could time out or become slow and inconsistent across models. | The supposed automation created review and repair overhead. | Test a small representative source first; select a model with sufficient context and reliability for the task; divide work into checkpointed steps; log incomplete work rather than assuming it finished. | Anna, 2026-06-29 to 2026-06-30 daily log; Julie, 2026-07-06 daily log. |
| LLM wiki | Quantitative values were extracted from the wrong context or inferred when unavailable. | A VJ20 cut-in speed was misreported and affected ranking; values in figures were particularly vulnerable. | Require the exact source location, units, operating condition, scale, and metric definition for every decision-relevant number. Verify it in the primary source before scoring or reporting it. Mark missing data as missing instead of estimating it. | Anna, 2026-07-06 and 2026-07-20 daily log; Julie, 2026-07-20 daily log; technical report draft, Section 4.3. |

| LLM wiki | General SimScale documentation supported basic learning but not specific CFD troubleshooting. | The wiki repeated known advice when it lacked condition-matched evidence. | Ingest targeted validation studies, authoritative manuals, relevant forum threads, and records of the team's own runs; seek expert review when the evidence remains insufficient. | Anna, 2026-07-15 to 2026-07-17 daily log. |

| LLM wiki | Initial quizzes focused on small details instead of conceptual understanding. | The assessment did not test the intended learning outcomes. | State the desired level and learning objective explicitly, for example: "test causal concepts and tradeoffs, not memorized materials or dimensions." Review and refine the first quiz. | Julie, 2026-06-29 daily log. |
| Obsidian and LLM wiki | Broken links, malformed wikilinks, inconsistent note names, and missing properties impaired navigation and data views. | Metadata and backlinks were part of the retrieval system, so formatting defects affected practical reliability. | Use consistent naming and templates; require Obsidian wikilinks for local notes; validate local links and unresolved targets after edits; audit required frontmatter/properties. | Anna, 2026-06-30 to 2026-07-03 daily log; Julie, 2026-07-01 to 2026-07-02 daily log. |
| Obsidian and LLM wiki | Automatic links to every technical term could create noisy graphs and unhelpful connections. | More links do not necessarily create better navigation. | Link key concepts deliberately and use tags/properties for design choices that must be compared; test whether a graph, backlink, base, or search view answers a real question. | Julie, 2026-07-01 daily log. |
| Obsidian and LLM wiki | Obsidian features can become setup work without a defined use. | Learning Dataview, bases, graphs, canvases, and metadata consumes time. | Begin with folders, tags, properties, search, and backlinks. | Obsidian and LLM wiki | Important context lived outside formal sources. | Without meeting notes, daily logs, and agent-chat exports, later documentation and troubleshooting lack decision history. | Store detailed daily logs, meeting notes, prompt records, and exported CAD-agent chats in the vault; include intent, changes, failures, observations, and open questions. | Anna, 2026-07-08 and 2026-07-21 daily log; Julie, 2026-07-10 and 2026-07-21 daily log. |
| General prompting | One request for a single answer can hide uncertainty and alternative framings. | The LLM may choose a plausible answer rather than expose the decision space. | Ask for multiple options, competing interpretations, explicit assumptions, and reasons one option could fail. Use personas or alternate weighting schemes to test sensitivity. | Anna, 2026-06-30 and 2026-07-10 daily log; Julie, 2026-07-10 and 2026-07-15 daily log. |
| General prompting | Work-plan requests produced insufficiently diverse results unless the prompt changed substantially. | Similar wording can produce conventional, clustered plans. | Request deliberately distinct plans based on named objectives or personas, then compare their assumptions. Use lower-probability sampling experiments only as idea generation, not evidence. | Anna, 2026-07-08 and 2026-07-17 daily log; `active/analysis/LLM Prompting Experiments.md`. |
| General prompting | A direct request for one exact fact could elicit an overconfident but wrong answer. | The model can match the shape of a request rather than the intended source context. | Ask for the reasoning, competing values, source context, and uncertainty before asking for a recommendation. Use the answer to direct human review rather than as the final fact. | Anna, 2026-07-20 daily log. |
| General prompting | Visual decision matrices could be vague and end by deferring to a human. | A polished diagram did not necessarily create an actionable next experiment. | Provide the available evidence, constraints, decision criterion, and required next action. Require branches tied to observable tests, owners, and stop conditions; reject generic branches. | Julie, 2026-07-21 daily log. |
| General prompting | AI-generated rankings can appear objective even when inputs are incomplete or inferred. | Quantitative scores can conceal weak evidence and human value judgments. | Define criteria and weights as human decisions; preserve independent human scores; label missing values; display evidence and assumptions; test persona/weight sensitivity; manually verify close or consequential outcomes. | Anna, 2026-07-09 to 2026-07-10 daily log; Julie, 2026-07-07 to 2026-07-10 daily log. |
| General prompting | Generic web-enabled AI gave more relevant troubleshooting ideas but had weaker provenance. | Broad retrieval can improve recall while reducing control over source quality. | Allow web search only after the curated wiki lacks coverage; clearly separate web findings from project-source claims; prefer authoritative sources and verify before adding them to project evidence. | Anna, 2026-07-16 and 2026-07-21 daily log. |
| AI-assisted CAD | Long, highly detailed CAD prompts created obvious first-pass geometry errors. | More instructions overloaded the request without guaranteeing adherence. | Use a short constrained prompt for the first model: fixed source-backed geometry, prohibited features, editable inferred items, coordinate conventions, and required deliverables. Add detail through focused revisions. | Anna, 2026-07-10 daily log; `active/documentation/CAD log/a_vj20.md`. |
| AI-assisted CAD | Generated CAD can look correct while containing disconnected, floating, missing, or incorrectly shaped components. | Render quality, successful execution, and fully constrained sketches do not establish mechanical coherence or source fidelity. | Inspect every revision with a checklist for dimensions, blade count, airfoil identity/orientation, phase, strut count, joins, gaps, overlaps, watertightness, and CFD-relevant faces. | `active/documentation/CAD Modeling Process.md`; `active/documentation/CAD log/a_vj20.md`. |
| AI-assisted CAD | A request to repair one feature could change unrelated geometry. | Undeclared collateral edits made models unstable and hard to trust. | Request one narrowly scoped change and "make no other changes"; ask the tool to report files and code lines changed; compare the revised model against a saved baseline. | Julie, 2026-07-10 daily log; `active/documentation/CAD log/a_vj20.md`. |
| AI-assisted CAD | The team initially lacked enough model understanding to make repairs confidently. | An opaque generated model makes manual correction and future iteration difficult. | Learn the CAD tool and underlying parametric language with simple exercises before relying on a complex model. | AI-assisted CAD | Source papers did not always provide complete CAD-ready geometry. | AI could convert missing dimensions into unjustified apparent precision. | Maintain a geometry ledger with source-backed values, derived values, editable inferred values, and unknowns that block faithful reconstruction. | AI-assisted CAD | Tool errors, server issues, slow interaction, and failed imports interrupted work. | Automation was not always faster than a manual edit, especially after repeated retries. | Timebox retries; keep exportable, versioned models; use the tool that best fits the task; switch to direct edits when a simple manual change is quicker; document tool-state failures separately from model defects. | Anna, 2026-07-10 and 2026-08-02 daily log; Julie, 2026-07-20 daily log. |
| AI-assisted CAD | Fusion produced a visually strong VJ20 model with the wrong inner airfoil; it also misoriented an airfoil despite explicit requests. | A visually persuasive model can be aerodynamically wrong. | Verify section coordinates, orientation, dimensions, and pitch in the model rather than relying on labels or renders. Preserve the source airfoil data and inspect the actual profile. | Anna, 2026-07-20 daily log; `active/documentation/CAD log/a_vj20.md`. |
| CFD and simulation AI | The LLM could not see the complete mesh, settings, and outputs simultaneously. | It repeated already-applied suggestions, conflicted with settings, and encouraged unnecessary simulation runs. | Maintain a structured run log with geometry, domain, mesh, solver, boundary conditions, results, and visual mesh evidence. Provide the relevant snapshot and exact current state, or use a tool that can inspect the model directly. | Julie, 2026-07-24 and 2026-07-27 daily log; Anna, 2026-07-17 daily log. |
| CFD and simulation AI | Generic advice was repetitive or did not diagnose a specific validation failure. | The source base and prompt context did not support a discriminating recommendation. | Ask for a ranked hypothesis list tied to the recorded setup and a single controlled next test. Add condition-matched studies; use direct documentation, a domain-specific assistant, or expert review for persistent failures. | Anna, 2026-07-15 to 2026-07-17 daily log; Julie, 2026-07-28 daily log. |
| CFD and simulation AI | AI generated an incorrect velocity from a Reynolds-number request. | A basic calculation error corrupted the simulation settings. | Independently calculate and unit-check all derived simulation inputs, then compare with the model's work. Record the formula, units, and assumptions. | Julie, 2026-07-20 daily log. |
| CFD and simulation AI | Simulation or tool checks could be mistaken for validation. | Convergence, a clean mesh, or a plausible coefficient does not prove that the physical setup or benchmark comparison is valid. | Define validation evidence in advance: matched geometry, dimensionality, reference area, operating conditions, mesh/domain sensitivity, convergence, and appropriate experimental or published benchmark. Escalate unresolved discrepancies to an expert. | `active/documentation/Technical Report Draft - 2026-08-03.md`, Section 6; Anna and Julie CFD daily-log entries. |
| Collaboration and records | AI output was difficult to reconstruct when prompts, rationale, and failures were not preserved. | Later reviewers could not distinguish source evidence, human decisions, agent assumptions, and tool claims. | Version the repository; save prompts, agent responses, source links, screenshots, generated files, and review results. Export AI-CAD chats into the project record. | Julie, 2026-07-10 daily log; `active/documentation/CAD log/a_vj20.md`. |
| Collaboration and records | Daily logs could be perceived as overhead rather than engineering work. | Without them, later documentation and handoffs lose the reasoning behind decisions and failed attempts. | Write short but detailed daily entries during the work: what changed, what was tried, what evidence was used, what failed, what was learned, and what remains uncertain. Use the log as context for summaries, handoffs, and retrospectives. | Anna, 2026-07-21 daily log; Julie, 2026-07-21 and 2026-07-23 daily log. |
| Collaboration and records | AI can create automation bias, anchoring, fluency bias, and sycophantic agreement. | A polished answer may be accepted because it is fast or confident rather than correct. | Build evaluation questions that target known failures; compare independent human reasoning with AI outputs; ask for disconfirming evidence; label uncertainties; and make a human explicitly accept or reject consequential outputs. | Anna, 2026-06-23 to 2026-06-26 daily log; `active/documentation/Blog Final.md`. |

## Prompting Patterns Worth Reusing

The project did not identify a single best prompt. Different prompt styles served different purposes and should be selected by the desired output and risk level.

| Intended result | Prompt pattern | Use and limit |
| --- | --- | --- |
| Source-grounded retrieval | "Answer only from the project sources. Cite each claim. For each quantitative value, give the source location, units, test conditions, and whether it is text- or figure-derived. State what is missing." | Use for research questions and design inputs. Verify primary-source values before decisions. |
| Conceptual learning | "Teach the causal idea at [beginner/intermediate] level, then ask one question that tests the tradeoff rather than recall. Do not reveal the answer until I respond." | Use to keep the human active rather than make the wiki an answer machine. |
| Diverse exploration | "Generate [number] materially different approaches. Give each a distinct objective/persona, assumptions, benefits, failure modes, and evidence needed to choose it." | Use for plans, concepts, and sensitivity analysis. The alternatives are hypotheses, not evidence. |
| Transparent decision support | "Create a comparison table using these human-defined criteria and weights. Keep missing data blank, mark inferences, show calculations, and identify which top-ranked results could reverse if uncertain inputs change." | Use for rankings. Preserve independent human scoring and verify close results. |
| Targeted troubleshooting | "Given this exact current setup and these observed results, rank the most plausible causes. For each, identify the evidence for and against it and one controlled next test. Do not repeat changes already listed as completed." | Use when the full state can be supplied. Escalate if the tool cannot inspect key visual or software evidence. |
| First-pass CAD | "Model only the stated source-backed geometry. Keep inferred hardware editable and label it as inferred. Do not add [prohibited features]. Deliver the parameter table, assumptions list, and specified views." | Use for fast, constrained geometry. Inspect every result independently. |
| Narrow CAD revision | "Change only [named feature] to [specified state]. Preserve [named invariants]. Report every file and line changed, then provide the checks performed." | Use to limit collateral edits and support manual review. |
| Documentation from logs | "Read these daily and technical logs. Extract actions, decisions, failures, evidence, and unresolved questions into an outline. Do not invent outcomes; retain dates or record references for each item." | Use for handoffs, reports, and retrospectives. Human authors must review the synthesis. |

## Limits and Next Checks

The recommendations are based on one evolving, short-duration VAWT project and reflect the available records rather than controlled comparisons of AI tools. Tool capabilities, models, interfaces, and project constraints may change. The strongest project-supported conclusion is procedural: trustworthy AI use required source traceability, explicit uncertainty, human inspection, and records of both failures and decisions. (source: `active/_anna daily log.md`; source: `active/_julie_daily_log.md`; source: `active/documentation/Technical Report Draft - 2026-08-03.md`)

Before reusing this appendix, a future team should test its source-ingestion procedure, link and metadata checks, quantitative-verification checklist, CAD inspection checklist, and simulation run-log format on a small pilot task. It should also define which outputs require primary-source review, independent calculation, geometry inspection, or expert sign-off before work begins.
